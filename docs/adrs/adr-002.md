# ADR-002: 判定服务先用 mock 实现，与真实客户端同签名

- **状态**: 已接受 (Accepted)
- **日期**: 2026-09-22
- **关联**: `03` §2.1、`05` §2.1 / §2.2 / §4、`300-design` §4.2 / §5

## 背景

`v0.1.0` 的核心链路是「抓 diff → 判定打分 → 阈值过滤 → 清单 → 跳转」，其中判定环节依赖外部决策服务。立项时该服务的接入参数（endpoint / 鉴权方式）尚未确认。

若把真实客户端作为前置条件，整条链路无法开工；若为 mock 单独设计一套简化接口，`v0.1.1` 接入真实服务时又要重写调用方、测试与契约。

## 决策

`v0.1.0` 的 `infra/jevClient` 先用**本地纯函数**实现，但公开签名与真实客户端**完全一致**：

- 对外只暴露 `decide(payload): Promise<DecisionResult>`
- 判定逻辑为本地「多维加权合成」（`300-design` §4.2）——恰好对应 Jev 官方推荐的 composite scoring 模式
- `v0.1.1` 接入真实服务时**只替换 `infra/jevClient` 的实现**，签名、调用方、测试结构均不变

## 原因

1. **接口层隔离**：`core/riskEngine` 依赖抽象（`IJevClient`）而非具体实现，mock 与真实客户端可互换——这也是 `01` §3 中 T1「依赖注入」Mock 策略成立的前提。
2. **与官方模式吻合**：Jev 官方文档明确推荐「把复杂判断拆成原子问题、在代码里组合权重」。本地加权 mock 与真实 `noul` question 的结构一一对应，不存在「mock 是临时的、真身要重新设计」的落差。
3. **风险已有预案**：`05` §4 已把「接入参数未确认」列为风险并给出「先用 mock 跑通链路」的应对；本决策是该预案的正式化。

## 后果

✅ 核心链路可在零外部依赖下开工并交付
✅ 测试无需网络，T1 可纯 Node 毫秒级运行
✅ `scoreHunk` 的签名与权重结构在 `v0.1.1` **不变**，测试用例与 Harness 数据可复用
⚠️ mock 权重是启发式初值，与真实判定质量存在偏差——须由 S2 Harness 用真实仓库数据实测、S3 回填（`dev-meta/docs/02-version-rules.md` §6.3「数据驱动阈值」强制要求）
⚠️ 存在「mock 全绿即以为功能完成」的自欺风险——`v0.1.1` 的真实接入与降级路径**必须**视为独立交付，不得因 mock 已绿而跳过
🔧 `v0.1.1` 替换实现时须同步启用 T2（网络层拦截），验证 `401` / `422` / `429` / `529` 的降级表现
🔧 本决策此前仅以表格形式登记在 `300-design` §5，编号需回填该表

## 替代方案

| 方案 | 否决原因 |
|---|---|
| 等接入参数确认再开工 | 阻塞整个 `v0.1.0`，且当时无法预估等待时长 |
| mock 用简化接口，`v0.1.1` 再对齐真实形态 | 调用方、测试、契约三处都要重写，成本远高于「一开始就按同签名造」 |
| 直接接入当时可用的第三方网关 | 引入未验证的外部依赖与计费；`v0.1.0` 的目标是验证产品价值，不是验证集成 |
