# ADR-003: 测试框架选型 —— Vitest + MSW

- **状态**: 已接受 (Accepted)
- **日期**: 2026-09-22
- **关联**: `01` §1 / §3、`300-design` §7、`400-build` §3.7

## 背景

`01` §3 定义了 T1（单元 / 断言）/ T2（契约 / 集成）/ T3（端到端 / 真机）三层测试职责，但框架选型一直是 TODO（`01` §1 测试框架行）。选型必须同时覆盖三类差异很大的场景：

- **T1**：纯 Node 逻辑（diff 解析、上下文截取、判定打分、阈值过滤、配置归一），要求毫秒级、不加载 `vscode`；
- **T2**：网络契约（`401` / `422` / `429` / `529` 的降级与指数退避、Header 拼装、超时计时），需要拦截真实 HTTP 请求但不发真实网络；
- **T3**：扩展宿主内的原生控件交互（QuickPick / 状态栏），无法在纯 Node 复现，只能真机验证（`300-design` §7）。

## 决策

- **测试运行器**：Vitest（`^5.0`）
- **网络层拦截**：MSW（Mock Service Worker，`^2.15`），仅用于 T2
- **T1 的 Mock 方式**：依赖注入——`core` 依赖 `IJevClient` 抽象，测试注入内存 stub，**不使用框架级模块 mock**
- **T3**：不纳入自动化框架，维持 `.vsix` 真机人工验证

## 原因

1. **单一运行器覆盖纯 Node 场景**：T1 与 T2 都在 Node 环境运行，不需要扩展宿主。Vitest 零配置支持 TS 与 ESM，而 mocha 需额外拼装 `ts-node` / `esbuild-register` 一类工具链。
2. **MSW 的拦截层级正确**：它在 **HTTP 层**拦截，因此客户端的 Header 拼装、超时计时、`429` / `529` 指数退避会**真实执行**——这正是 T2 要验证的内容。若改为 mock 掉 `fetch` 函数，退避与超时会被一并跳过，等于没测。
3. **T1 与 T2 的 Mock 层级必须分开**：T1 求快，故用依赖注入（最浅）；T2 求真，故用 HTTP 拦截（最深）。混用会让「测过的」与「未测的」边界模糊。
4. **不选 `@vscode/test-electron` 覆盖 T1/T2**：它会启动真实 VS Code 实例，单次运行以秒计——用于纯逻辑测试是数量级的浪费；其价值在 T3，而 T3 按设计走人工。
5. **与 `01` §2 依赖约束相容**：两者只进 `devDependencies`，不进入扩展运行产物。

## 后果

✅ T1 可在毫秒级完成，适合作为 S6 的提交前门禁（`400-build` §3.7）
✅ T2 能真实验证 `401` / `422` / `429` / `529` 的降级与退避，而非「假设它工作」
✅ 单一配置同时支持 TS 与 ESM，降低工程骨架复杂度
⚠️ MSW 在 Node 环境需显式 setup / teardown（可能替换全局 `fetch`），S6 落地时须确认用例间隔离，避免串扰
⚠️ Vitest 与 mocha 的断言 / 生命周期 API 不同；若后续需要官方 VS Code 测试脚手架（依赖 mocha 生态），须评估并存成本
🔧 依赖登记：`vitest ^5.0`、`msw ^2.15` 进 `devDependencies`，随 S0 的 `package.json` 改动一并加入
🔧 回填 `01` §1 的测试框架行与 §3 的运行命令（`npm run test:unit` / `npm run test:integration`）

## 替代方案

| 方案 | 否决原因 |
|---|---|
| mocha + chai + `@vscode/test-electron` | 官方模板默认，但 T1/T2 会被迫跑在真实 VS Code 实例中，速度以秒计；且需额外拼装 TS 工具链 |
| Jest | TS + ESM 配置成本高于 Vitest；且无内建网络层拦截，仍需 MSW 或 `nock` |
| Vitest + `nock` | `nock` 拦截 Node `http` 模块，对原生 `fetch` 需额外适配；MSW 面向 `fetch` 的抽象更直接 |
| 不引 MSW，T2 直接 mock `fetch` 函数 | 会跳过退避与超时逻辑，使 T2 退化为「测试 mock 自身」，丧失契约验证价值 |
