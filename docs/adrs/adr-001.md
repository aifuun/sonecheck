# ADR-001: 扩展工程迁移到 TypeScript

- **状态**: 已接受 (Accepted)
- **日期**: 2026-09-22
- **关联**: `01` §1、`02` §1、`300-design` §2.1 / §5、`400-build` §3.1

## 背景

`extension/` 初始为纯 JavaScript 占位（`extension.js` 仅注册一个 `sonecheck.showStatus` 命令）。`v0.1.0` 要落地三层架构（`ui` / `core` / `infra`）与 `03` §1 的七条不可变式，这些约束需要类型系统在编译期兜住：

- 层间只交换项目自有类型（`Hunk` / `RiskItem` / `DecisionResult` / `SoneCheckConfig`），防止 `vscode` 类型漏进 `core`；
- `GUARD-01`（`core` 不得引用 `vscode`）与 `GUARD-02`（配置读取唯一出口）需要可静态检查的模块边界。

## 决策

`extension/` 迁移到 TypeScript，编译布局为 `src/` → `out/`：

- `tsconfig.json`：`target: ES2022`、`module: commonjs`、`rootDir: ./src`、`outDir: ./out`、`strict: true`、`sourceMap: true`
- `package.json` 的 `main` 指向 `./out/extension.js`
- `.vscodeignore` 排除 `src/`、`test/`、`tsconfig.json`、`**/*.map`

## 原因

1. 与 `01` §1 的技术选型一致——语言 / 运行时已定为 TypeScript + Node 22。
2. `src` + `out` 是 VS Code 官方扩展模板的惯例布局，后续查文档、抄官方示例零摩擦。
3. 类型系统是 `03` §1 七条不变式的**编译期执行手段**——没有类型边界，`GUARD-01` / `GUARD-02` 只能靠 `grep` 事后补救。

## 后果

✅ `core` / `infra` 的层级纪律可被编译期与守卫双重约束
✅ 契约中的 `Hunk` / `RiskItem` / `DecisionResult` / `SoneCheckConfig` 成为真实类型，契约与实现不易漂移
⚠️ 引入构建步骤，调试链路变为「改 `src/` → 编译 → 运行 `out/`」；S0 后须立即验证 Extension Development Host 能加载（`400-build` §4 已登记该风险）
⚠️ 源码与产物分目录，`.vscodeignore` 必须同步维护，否则会打包进源码
🔧 本决策此前仅以表格形式登记在 `300-design` §5，本 ADR 为其正式落盘，编号需回填该表

## 替代方案

| 方案 | 否决原因 |
|---|---|
| 保持纯 JavaScript | 无法在编译期执行 `03` §1 的层级与类型边界；契约类型只能靠 JSDoc 手写，无强制力 |
| TypeScript + `src/` → `dist/` | 与官方模板默认不一致，抄示例时需反复改写路径；收益为零 |
