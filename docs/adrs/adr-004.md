# ADR-004: Jev 客户端手写 fetch，不引入官方 SDK

- **状态**: 已接受 (Accepted)
- **日期**: 2026-09-22
- **关联**: `03` §2.1、`01` §2、`06` §2

## 背景

Jev 官方提供 Python 与 JavaScript SDK，其**默认重试策略已自动处理** `429` / `529` 退避（见官方 API reference 的 Rate Limits 一节）。采用官方 SDK 可免写重试逻辑。

本项目对 `infra/jevClient` 的需求面极窄：**单一 `POST` 端点、单一请求形态、三类返回原语**。

## 决策

`infra/jevClient` **手写 `fetch` 调用** + 小段指数退避函数，不引入官方 JS SDK：

- `POST https://api.typesafe.ai/v1/systemone`，`Authorization: Bearer <API_KEY>`
- 超时用 `AbortController` 实现（上限见 `03` §2.1）
- **仅**对 `429` / `529` 做指数退避（次数上限见 `03` §2.1）
- `401` / `422` / 其它非 2xx 分别归入 `ERR-04` / `ERR-05` / `ERR-03`，**不重试**

## 原因

1. **调用面极窄**：一个端点、一种方法。SDK 带来的抽象收益小于它引入的依赖体积与版本漂移风险。
2. **与 `01` §2 的依赖约束一致**：运行期依赖越少，扩展包体积越小、企业安全审查阻力越低——目标用户是隐私敏感的企业开发者（`00` §2 US-04）。
3. **退避逻辑必须自己掌握**：`03` §2.1 要求按错误码区分处理，且 `06` §2 要求对 `retryCount` 埋点。SDK 内置退避是黑盒，难以观测。
4. **零运行期新增依赖**：`fetch` 是 Node 18+ 的原生全局。

## 后果

✅ 运行期零新增依赖，扩展包体积与供应链风险不变
✅ 退避与超时逻辑显式可见，可按 `06` §2 埋点（`httpStatus` / `retryCount`）
✅ 错误码到 `ERR-*` 的映射完全由本项目控制，不受 SDK 语义变化影响
⚠️ 需自行处理 Node `fetch` 的边界：`AbortController` 超时、连接复用、非 2xx 时的响应体读取
⚠️ 上游若调整认证方式或新增必需 Header，需手工跟进（SDK 用户可借升级自动获得）
🔧 `03` §2.1 的两处 TODO（超时上限、退避次数上限）须由本地实测定案
🔧 若上游未来提供批量评估等复合端点，须重新评估本决策（可能构成 Superseded）

## 替代方案

| 方案 | 否决原因 |
|---|---|
| 使用官方 JavaScript SDK | 唯一收益是免写退避函数；代价是运行期依赖 + 退避过程黑盒、不便埋点 |
| 经 Vercel / Cloudflare / OpenRouter 网关调用 | 增加一跳网络与一个第三方依赖；网关的聚合价值在 v0.1.x 用不上 |
| 手写 fetch 但引 `p-retry` 等重试库 | 为一个依赖换取少量逻辑不划算；且会掩盖「哪些状态码该重试」这一契约要点 |
