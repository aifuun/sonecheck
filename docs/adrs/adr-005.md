# ADR-005: 风险分采用 `noul` 原语，不使用 `score` 原语

- **状态**: 已接受 (Accepted)
- **日期**: 2026-09-22
- **关联**: `03` §2.1 / §2.4 / §3、`300-design` §4.2、`04` §1

## 背景

Jev 提供三种问题原语：

- `noul`：是/否判断，返回 0–1 概率
- `choice`：从带标签选项中选一个，返回 `choice` + `probabilities` + `confidence`
- `score`：按**有序谱系**打分（2–10 级），返回概率加权值（**可落在两级之间**）+ `legend` + `probabilities` + `confidence`

本项目需要产出一个「风险分」，并与用户可配置的 `riskThreshold`（默认 `0.85`，见 `03` §3 `CFG-01`）比较，决定该块进入 `AUDIT` 还是 `PASS`。

## 决策

- 风险分使用 **`noul` 原语**（question key = `risk_score`）
- 风险归因单独使用 **`choice` 原语**（question key = `reason_code`），其 `criteria` 的 key 集合即 `03` §2.4 的枚举
- `decision` 不在 API 中，由本地按阈值派生（见 `03` §2.1）

## 原因

1. **阈值比较需要连续量**：`noul` 直接给出 0–1 连续概率，与用户设定的浮点阈值天然可比；`score` 返回的是「跨等级的加权值」，量纲由等级数决定（如 3 级时范围 0–2），与 `0.85` 这类阈值不直接对应，需再做一次归一化映射。
2. **避免双重概率语义**：`score` 同时返回「加权值」与「各等级概率」，而本项目的判定语义是「这个改动有多大风险」——用单一连续概率表达最直接，无需引入等级体系作中间层。
3. **`legend` 在 v0.1.x 无消费场景**：`score` 的等级描述适用于向用户解释「打了几级」；而本项目 UI 只展示 `[score] 文件:行 · reason`（`04` §1），归因已由 `reason_code` 承担，等级文字无处呈现。
4. **与 mock 的量纲一致**：`300-design` §4.2 的本地加权 mock 产出 `Σ(维度值 × 权重)` 截断到 `[0,1]`——与 `noul` 语义完全对齐，`v0.1.1` 换真实实现时无需改变量纲。

## 后果

✅ `scoreHunk` 的返回语义（0–1）在 mock 与真实实现之间保持一致，换实现不动量纲
✅ `riskThreshold` 的约束 `0.0 < v < 1.0` 与 `noul` 天然匹配，无需额外量纲说明
⚠️ 丧失「风险等级描述」这一可解释性来源——若未来 UI 需展示「高危 / 中危 / 低危」，须在本地按阈值切分，而非依赖模型返回的 `legend`
⚠️ `noul` 的 `criteria.true` / `criteria.false` 语义必须写清楚，否则「0.91」的正负方向会产生歧义
🔧 `03` §2.4 的 `reason_code` 枚举值必须与 `choice` 的 `criteria` key **逐字一致**，否则触发 `ERR-05` 丢块

## 替代方案

| 方案 | 否决原因 |
|---|---|
| `score` 原语 + 本地归一化到 0–1 | 需一次映射，且映射规则本身成为新的口径来源；`legend` 与 `probabilities` 两处均无消费 |
| `noul` 给风险分 + `score` 给严重度分级 | 两个原语回答高度重叠的问题，增加调用成本与 UI 负担；v0.1.x 无分级展示需求 |
| 用 `choice` 直接给出 `AUDIT` / `PASS` | 把阈值决策交给模型，用户无法调整 `riskThreshold`——与 `CFG-01` 的可配置阈值设计冲突，且丧失本地可判别性 |
